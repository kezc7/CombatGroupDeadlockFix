# Audit: Combat Group Deadlock Fix 1.0 → 1.1

> Version names: "1.0" in this document is the private development build of 2026-10-09 and "1.1" is the audited code, released publicly as **1.0.0**.

Date: 2026-10-11. Target: Skyrim AE 1.6.1170 (`SkyrimSE.exe` 1.6.1170.0), CommonLibSSE-NG v7.0.0.
Technical reference: [TECHNICAL.md](TECHNICAL.md).

## 1. Verdict

**Experimental beta, after one in-game smoke test. Hold a full ("stable") release until the in-game test plan has been run.**

**What is now known, not assumed:**
- The game's `BSReadWriteLock` protocol. All four functions were read from 1.6.1170 machine code.
- The full body of ID 44706, and how all 32 statically discoverable consumers read its result.
- The traced deadlock's call chain and lock order, every edge confirmed in the code.
- 1.1's read-lock leaves the lock word exactly as the game's own code does, in every state tested. This was shown by running the game's lock code itself, under real threads.

**What is not known:**
- Whether the fix resolves the freeze in the running game.
- Whether a forced "not a target" causes a lasting AI change at any of the 33+ callers.

Neither can be settled without playing the game. No in-game run of 1.0 or 1.1 is on record in the repository.

## 2. Findings (1.0)

| # | Severity | Finding | Status |
|---|---|---|---|
| F1 | **High** | Fast-fail mode treated a lost CAS race with another **reader** as a failure. For 2 s after any give-up, the thread answered "not a target" with no writer present. In `locktest`, 1.0 failed **43k–145k of 300k** tries with only readers around (14–48%). | Fixed |
| F2 | **High** | The fast-fail state was keyed only on the lock's address plus 2 s. It applied to any later short write hold by any thread, and to a new `CombatGroup` allocated at the same address. These false answers were never logged. | Fixed |
| F3 | Medium | `UsesAddressLibrary()` declares version independence, so SKSE loads the plugin on any AE runtime. That includes 1.7.x, which is installed on this machine. Only the byte checks stood between that and a patch. On a runtime with no Address Library file, CommonLib's database load fails fatally inside `SKSE::Init`. | Fixed |
| F4 | Medium | The replacement reproduces the lock protocol, but the game's lock functions (68233/68234/68239/68240) were never checked. A mod that changed them would leave the two sides with different protocols, a mutual-exclusion risk. | Fixed |
| F5 | Low–Med | Only ~30 of 44706's 166 bytes were checked. The data offset `+0x08` and the handle-first comparison were among those not checked. | Fixed |
| F6 | Low | The function returned a C++ `bool`, which only defines `al`. The game's returns `movzx eax, dil`. All 32 known consumers test `al`, but the callers of virtual `38560` can't be listed statically. | Fixed |
| F7 | Low | Reader races slept (`Sleep(0)`) where the game retries at once. | Fixed |
| F8 | Low | The DLL's version resource read 0.0.0, because `xmake.lua` had no `set_version`. | Fixed |
| F9 | Low | The packaging script built whatever mode was configured but copied from the `release` folder, so it could package a stale DLL. There was no test gate. | Fixed |
| F10 | Info | The documentation said a give-up happens "only during the deadlock" and that "the next AI update corrects it". In fact the timeout applies to every one of 44706's 33+ consumers, on any write hold of 500 ms or more, and lasting effects weren't traced. | Docs corrected |
| F11 | Info | "Each gave-up line is a freeze the fix stopped." A give-up proves a write hold of 500 ms or more, not a deadlock. | Docs corrected |
| F12 | Info | A count with bits 28..30 set makes the game's reader spin forever. That state is unreachable (it takes 2^28 holds). 1.1 times out on it instead. | Hardened |

No memory-safety defect was found:
- The replacement makes the same reads, in the same order and under the same lock, as the original.
- The handle function's out-parameter lives on the stack.
- Nothing is allocated on the fast path.
- Code is patched only during `SKSEPlugin_Load`, before game threads run it.

## 3. Bethesda lock verification

Done from the decrypted 1.6.1170 code section and confirmed against 1.0's live-game patterns; details in [TECHNICAL.md](TECHNICAL.md#the-games-bsreadwritelock-verified). Results:
1. **Layout:** writer thread id at `+0`, count at `+4`. Matches CommonLib.
2. **Writer id:** a plain store after the writer bit is set, then `mfence`. Cleared before the count is released.
3. **Readers:** the low bits of `count`.
4. **Writer bit:** `0x80000000`. A first write hold makes `0x80000001`.
5. **Reader acquisition:** `cmpxchg(count & 0x0FFFFFFF → +1)`. **The mask matches exactly.** No reader gets in while the writer bit is set.
6. **Writer acquisition:** only from `count == 0`.
7. **Nesting:** the writer may nest reads and writes. Readers nest freely, and `44704` relies on this.
8. **CAS:** `lock cmpxchg`.
9. **Unlock:** `UnlockForRead` is exactly `lock dec [lock+4]` in every state. `InterlockedDecrement` is therefore a precise reproduction.
10. **Ordering:** every count change is a lock-prefixed instruction, a full barrier on x64.
11. **Fairness:** there is no pending-writer state, so readers can starve a writer. That is the game's design and is unchanged.
12. **Overflow:** see F12.

**Can 1.1 read-lock while a writer is pending or active?** There is no "pending" state in the game's lock. While a writer is active, no: the CAS requires bits 28–31 clear.

## 4. Replacement function

Confirmed for 44706:
- **Signature:** `(CombatGroup* rcx, TESObjectREFR* rdx) → 0/1 in eax`, Windows x64 convention.
- **Order:** lock, then handle (via `37476`, as called by the original), then scan, then unlock.
- **Scan:** count `[+0x18]`, data `[+0x08]`, stride `0xA8`, handle at `+0`. These agree with CommonLib's `CombatGroup`/`CombatTarget` and with the code. The scan runs under the read lock, as in the original.
- **Null handling:** no null-group check, as in the original; `38571` checks before calling.
- **Object lifetime:** the same as the original.
- **Compiled code:** inspected; every return path writes all of `eax`.

**Hook:** `write_branch<5>` at the entry overwrites 5 checked bytes. A plugin that patched 44706 earlier makes 1.1 refuse to install. A plugin that patches it later sees a `jmp`, and its own checks decide what it does.

## 5. Risks of returning `false`

- **On the deadlock path:** `37534` (hostility) loses one "is a target" signal. It falls back to its other checks for one actor. `27293`'s search may skip that actor in this walk.
  - That is one query result; it doesn't write AI state itself. The next update asks again.
  - What `39578` does with "found nobody" once was not traced further.
- **Elsewhere:** 33+ consumers. Most were not traced to their effects.
  - Exposure only comes after a write hold of 500 ms or more, which in vanilla is already a long stall.
  - `44704`'s call can never time out, because it holds a read on the same group.
  - A lasting effect elsewhere can't be ruled out statically. **This is the main open risk.**

## 6. Timeout strategy

- **500 ms:** kept.
  - It is a judgement: a write hold that long is already a visible hitch, and it bounds the deadlock hitch.
  - There is no in-engine measurement of legitimate hold times. 1.1 logs successful waits of 100 ms or more to collect one.
- **Quick give-ups:** kept, because they are needed. The walk asks up to twice per entry, all under the lock the writer is waiting for.
  - They are now restricted to: the same writer, asks back to back (no 50 ms gap), and within 2 s. This addresses F1/F2 and stale state.
  - Remaining staleness: a new hold by the same writer thread within 50 ms of the last ask. A thread id can't tell holds apart, and the lock has no generation counter.
- **New synchronization problems:** none found.
  - A give-up never touches the lock.
  - Stress testing with the game's own writers showed no mutual-exclusion violation.
  - The give-up shifts no lock order: the replacement takes locks in the same order as the original.

## 7. Alternatives

Considered and rejected:
- reordering locks;
- try-locking on thread A's side, which drops a knowledge entry (persistent);
- deferring the knowledge write;
- releasing the AI-data lock mid-walk (a memory-safety risk);
- hooking only the three call sites in `37534`, which is narrower but leaves other readers exposed.

The bounded read in 44706 stays the safest practical option. Details: [TECHNICAL.md](TECHNICAL.md#alternatives-considered).

## 10. Tests executed

- **`locktest`, a simulation:** 61 checks, all passing, in 8 consecutive runs. It runs a C++ model of the game's lock, written from its documented behaviour, in a test process, not the game. Coverage is listed in [TECHNICAL.md](TECHNICAL.md#testslocktestcpp-simulation-not-the-game).
- **Static analysis of the 1.6.1170 code:**
  - lock functions;
  - 44706;
  - all callers of 44706 and 38571, and how they read its result;
  - lock holding in 44704 and 44711;
  - every edge of both traced call chains;
  - the per-entry loop in 39578;
  - lock use in 39515 and 39578.
- **Not executed:** anything in the game.

## 11. Remaining validation

1. **In-game smoke test (required before any upload):** check the `installed at SkyrimSE+803DF0` line, then fight for an hour with no regressions.
2. **The in-game test plan** in TECHNICAL.md (battles, followers, combat start and end, deaths, cell transitions, long sessions, AI mods), before a stable release.
3. **Ideally, a reproduction of the freeze with 1.1 installed:** a give-up logged, then combat carrying on. Until then, the fix's effect on the actual freeze is inferred, not observed.
4. **Slow-wait statistics from normal play,** to confirm or revisit the 500 ms limit.
5. **Resolved: no game code in the repository.** The install check compares length and FNV-1a 64 fingerprints (`src/GameFingerprints.h`), and the lock test runs a model of the lock, so no Bethesda code is in the source, the DLL or the history.

## 12. Recommendation

- **Hold** a stable release.
- **Experimental beta** is appropriate once item 1 above passes, clearly labelled as such (the Nexus text is written that way).
- The engine-facing semantics are no longer materially uncertain. The open questions are behavioural and can only be answered in game.
